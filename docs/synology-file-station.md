Create a saved **HTTP** or **HTTPS** connection, choose **Protocol → Application → Synology DSM**, then choose **Synology NAS API** in its access settings. Opening the connection embeds the API view in its session tab, without a second enclosing dialog or close button. **File Station** is its file-management section; the other tabs expose supported NAS administration. The session owns its NAS client: two open NAS tabs do not replace one another. The saved target is fixed for that session; edit the connection to change host, port, or transport.

The standalone **Synology NAS API** window also remains available: enter the NAS hostname, DSM port, username and password, then choose **Connect**. File Station opens at the shared-folder list; open a share to manage files. Administration tabs use the same authenticated session when your account has permission.

## Sign in and two-factor authentication

HTTPS is enabled by default on port **5001** and verifies the server certificate. Use the hostname covered by the certificate and a trusted certificate chain. Certificate errors are not bypassed. Explicitly choosing HTTP leaves the port unchanged and sends credentials without TLS encryption.

QuickConnect NAS aliases, such as `your-nas.quickconnect.to`, are resolved anonymously before sign-in. The resolver only selects an admitted same-NAS HTTPS endpoint after identity and API checks; it does not navigate the DSM website or reuse its cookies. Even an HTTP QuickConnect landing alias resolves through verified HTTPS. Discovery and any bounded relay setup use the same selected app-wide route as the later API session. A failed resolution never sends credentials to the provider or falls back to an unrelated endpoint. See [native API resolution and session status](synology-file-station-sessions.md#quickconnect-api-resolution) for the bounds and anonymous gateway fallback.

On DSM 7 the app signs in the way DSM's own sign-in page does: it completes DSM's secure login handshake and signs the session's administration requests. DSM gives a session opened without the handshake, for example over QuickConnect or a remote address, only limited API access, so even an administrator can find data marked **Session restricted**. If the NAS doesn't offer the handshake (DSM 6 and older DSM 7 releases) or doesn't complete it, sign-in continues without it and the session panel says so. See [secure login handshake](synology-file-station-sessions.md#secure-login-handshake).

DSM has no resumable sign-in, so each attempt, including each code you submit, is a complete new sign-in with a fresh handshake. DSM's answer decides what happens next:

| DSM answer (code)                | What you see                                                    | What to do                                                                                                                                            |
| -------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wrong username or password (400) | A sign-in error                                                 | Check the saved or entered username and password.                                                                                                     |
| Account disabled (401)           | "The DSM account is disabled."                                  | Ask a DSM administrator to enable the account.                                                                                                        |
| API sign-in refused (402)        | A note that the NAS API view signs in as a File Station session | Check the account's File Station application privilege and DSM login restrictions.                                                                    |
| Code required (403)              | **Two-factor authentication** with a code field                 | Enter the current code from your authenticator app, or the code shown in Synology Secure SignIn.                                                      |
| Code not accepted (404)          | The same dialog: "The one-time code was not accepted."          | Enter a fresh code, or choose **Cancel sign-in**.                                                                                                     |
| Two-factor setup required (406)  | **Two-factor setup required**, with no code field               | The account must set up two-factor authentication first. Complete setup once in DSM in your browser (the DSM website view works), then connect again. |
| Address blocked (407)            | A blocked-client-IP error                                       | Ask a DSM administrator to unblock this computer's address.                                                                                           |
| Password expired (408, 409, 410) | An expired or must-change password message                      | Change the password in DSM in your browser. If the account can't change its own password (408), ask a DSM administrator to reset it.                  |
| Unsupported sign-in method (449) | **Sign-in method not supported**, with no code field            | Use the connection's **DSM website** access mode for this account.                                                                                    |

Codes are cleared after every attempt and never saved. **Cancel sign-in** clears the pending password and code. With a vault authenticator selected for a saved connection, the app generates one code only after DSM asks for it and submits it once; a rejected code is not retried automatically. See [Synology API versus DSM website](credential-vault-portability.md#synology-api-versus-dsm-website). The sign-in never enrolls authenticators or generates website recovery codes.

Of DSM's second factors, the API can complete only one-time codes. **Approve sign-in (Secure SignIn push), security keys and passkeys can't complete an API sign-in.** After DSM asks for a code or refuses the method, the app asks DSM once which sign-in methods the account has and lists them in the dialog as **One-time code**, **Secure SignIn approval** or **Security key**. If the account can also use a code, enter it; otherwise use the **DSM website** view, which hands those steps to you on DSM's own page (see [Two-factor and Secure SignIn steps](synology-file-station-sessions.md#two-factor-and-secure-signin-steps)). Approving a sign-in in a browser doesn't authorize the API session. When DSM doesn't report the methods, the dialog shows the general guidance. See Synology's [DSM login API guide](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Os/DSM/All/enu/DSM_Login_Web_API_Guide_enu.pdf) and [two-factor authentication documentation](https://kb.synology.com/en-global/DSM/help/DSM/SecureSignIn/2factor_authentication?version=7).

### Trust this device

In the code dialog of a saved connection, **Trust this device for this NAS account** asks DSM to remember this computer once the code is accepted. Later sign-ins from this computer then skip the code, including **Connect** after the session expires. It is off by default. Automatic vault-authenticator sign-ins show no dialog; to trust the device for those, turn on **Trust this device after a successful two-factor sign-in** in the connection's Synology access settings. The dialog checkbox still changes it for a single sign-in. A notice confirms the result, or tells you that DSM didn't issue a trusted device, in which case the next sign-in asks for a code again.

- **Vault only.** The connection's credentials must be in the credential vault; for local credentials the option is shown disabled. DSM's device token is stored only in that vault entry, encrypted with the owning database. It never goes in the connection record, the page or error text, and it is never displayed.
- **Not portable.** Encrypted vault archives never include trusted devices, and importing an archive drops any it contains. Database exports refuse vault data.
- **Bound to this computer's name.** DSM lists the device as `SortOfRemoteNG · <computer name>`, and the app sends the token only when that name matches this computer. The same database on another computer, or a renamed computer, asks for a code again and forgets the saved device. One device is kept per NAS address and account, so a database used on two computers makes each computer trust itself again in turn. This check prevents silent reuse of a copied database; it does not protect against someone who has the unlocked database.
- **macOS.** The app usually can't read a Mac's computer name, so every Mac is named `SortOfRemoteNG · desktop` and the name check can't tell two Macs apart.
- **No longer accepted.** When DSM rejects the saved device, for example after it was removed in DSM, the app forgets it, shows "This NAS no longer accepts the saved trusted device", and asks for a code. A vault authenticator is still tried at most once.
- **Forget it.** While connected, choose **Forget this device** in the trusted-device bar. On the sign-in screen, choose **Forget trusted device**. In the vault, open the entry's **Trusted NAS devices**, choose **Forget trusted device**, then save. Forgetting only removes the app's copy: to revoke the device on the NAS, sign in to DSM, open **Personal › Security** and remove it from the account's trusted devices.

## Manage files

- Browse with folder names, breadcrumbs, the parent-folder button, or an absolute NAS folder path. Lists use pages of up to **100** entries with name, size, type and modified-time sorting.
- Search within an open shared folder. Search results are paginated; clear the search field and choose **Search** to return to the folder list.
- Select individual entries or the current page. Create folders, rename one entry, or review a multi-selection before copying, moving or deleting it. Copy and move require an existing absolute destination inside a share.
- **Upload** opens the native local-file chooser. **Download** saves one selected file through the native Save dialog: choose a **new filename**, because existing local files are never overwritten, even if the operating-system dialog offers overwrite confirmation. Cancelling the dialog is not reported as a successful transfer. Existing destination files are not overwritten or silently skipped.

Copy, move, delete and search wait for the NAS task's completion, not merely acceptance of the request. Known progress is shown; **Cancel task** requests cancellation without undoing changes already made. Inspect the NAS afterward. Failed cancellation remains visible and can be retried. No file operation is automatically retried.

**Details & permissions** displays the selected listing's owner, group, size, timestamps, real path, POSIX mode and ACL mode where supplied. Missing metadata is unknown. ACL editing is not exposed. **Share selected item** reviews the selected path before creating a link, with an optional password of up to 16 characters and an optional expiry date. **Sharing links** lists up to 50 links per NAS page and supports explicit, individually confirmed revocation. Links are not automatically opened. Sharing passwords are transient, and revoking a link does not delete its file. These bounds follow the [File Station API guide](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf).

Delete recovery depends on the NAS shared-folder recycle-bin configuration and is not guaranteed. NAS shared folders are administered separately in **Shares**, with distinct create/delete and encrypted-share lock/unlock confirmations. Permissions, quotas, installed packages, licenses and DSM version can limit individual operations.

Changing or disconnecting the NAS invalidates open action reviews. Native operations are tied to both the viewer instance and the captured session, including after local file dialogs; stale callbacks cannot operate on a replacement NAS. Saved-session operations also check current access to the owning database. Locking, switching or closing that database revokes its session. A definitive expired DSM session requires signing in again; mutations are never automatically replayed. Closing the viewer clears pending login secrets and requests cleanup of owned tasks and sessions. Merely hiding a tab pauses administration polling without signing out or cancelling a running NAS task.

## Administration and availability

Native Synology support requires a desktop build with the `ops` and `platform` capabilities (the `full` / `full-dev` profiles include them). Before credentials are resolved, the app also requires the running backend's versioned `syn_fs_transport_capabilities` marker to confirm HTTP proxy and QuickConnect support. A missing or old marker requires restarting/updating the desktop app; reloading its web page or retrying a password cannot add native commands. Developers must rebuild and relaunch the desktop process.

The native explorer supports the app-wide direct route or configured HTTP(S) proxy, with the same route and private NAS cookie jar retained for the session. It does not consult environment proxy settings or silently bypass a failed proxy. Changing the app-wide proxy requires reconnecting. Per-connection proxy/VPN/tunnel chains and custom browser certificate exceptions remain unsupported and are refused visibly; HTTPS uses verified system TLS. Use the **DSM website** access mode when a browser-based sign-in is more appropriate. Its authentication remains separate from the API session, and neither passwords nor one-time codes are retried automatically. This is not a guarantee of compatibility with every DSM version or installed package.

Tables provide local search and 25-row display pages. System and connection logs additionally expose 100-entry NAS pages. Visible administration views refresh every 30 seconds, with overlapping refreshes suppressed and manual **Refresh** available. A **—** cell means DSM didn't report that value; it is not zero. When a read fails for a reason other than access, **Some data could not be refreshed** lists each failed read with its API failure details and **Copy diagnostics**. Its values are cleared so stale data isn't shown, and **Refresh** tries it again. An expired session, missing package, access restriction or incompatible response is never shown as successful empty data. The last checked time describes the most recent refresh attempt, not a health guarantee.

Actions are explicit forms, not arbitrary API execution. Row buttons prefill the target's actual ID. Every write is reviewed with its target NAS and effect; acknowledgement means the NAS accepted the request, not that a reboot, package installation, backup or image download has finished. Inspect the refreshed status. File tasks separately poll their documented completion flag. Camera snapshots are bounded PNG/JPEG previews, not recording downloads. Container project start and stop accept the project's name or its id.

Download-task deletion's **Move incomplete files to destination** option is deliberately off by default. It controls Synology's `force_complete` behavior; it does not validate or complete partial content. See the [Download Station API guide](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/DownloadStation/All/enu/Synology_Download_Station_Web_API.pdf).

### Access checks and restricted data

The sidebar checks each section's reads once per API session, with at most three checks in flight, and pauses while the session tab or app is hidden. Every read is checked on its own, so a section counts as available only when all of its reads are. A check sends the same request its table loads, asking for one row where the table pages. Once per sign-in it also asks DSM whether the account is an administrator; that answer only chooses the explanation and never hides data DSM allows. A section check takes at most 10 seconds and each read at most 3 seconds, plus up to 5 seconds for the administrator lookup. A read that doesn't answer in time is **Could not verify**, not a denial.

| Read state                         | Meaning                                                                                                                                                                                                                | What to do                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Available                          | DSM returned the data.                                                                                                                                                                                                 | Nothing. Changes are still checked by DSM when each action runs.                                                                    |
| **Requires administrator**         | DSM allows this API only for administrators or accounts with a matching delegated administration role, and DSM didn't report the account as an administrator.                                                          | Sign in with an administrator account, or give the account a DSM delegated administration role that covers this data.               |
| **Session restricted**             | DSM refused the data for this API session although it reports the account as an administrator, or the session was opened through a DSM application portal.                                                             | See [Session restricted or requires administrator](synology-file-station-sessions.md#session-restricted-or-requires-administrator). |
| **Requires application privilege** | The API needs the File Station, Download Station or Surveillance Station application privilege.                                                                                                                        | Grant it in DSM **Control Panel › Application Privileges**, then recheck access.                                                    |
| **Permission denied**              | DSM refused the data (code 105) for another reason, for example when the application privilege is already granted.                                                                                                     | Review the account's DSM permissions, then recheck access.                                                                          |
| **Package not installed**          | The package that provides the API is not installed or not running: Container Manager, Virtual Machine Manager, Hyper Backup, Active Backup for Business, Download Station or Surveillance Station. No request is sent. | Install or start the package in DSM, then recheck access.                                                                           |
| **Not provided by this DSM**       | This DSM version doesn't provide the API, method or version, for example the notification settings read.                                                                                                               | Nothing; this data isn't available on this DSM.                                                                                     |
| **Could not verify**               | A timeout, network error, unexpected response, or a DSM code that doesn't identify a permission problem. The table still loads.                                                                                        | Use **Recheck access** or **Refresh**, and copy the diagnostics if it persists.                                                     |

In the sidebar, a fully readable section shows a check mark. **Partial access** keeps the section in the list: readable tables show their rows and the others show a notice. A section with nothing readable moves to one of two collapsed groups, **Needs more access (n)** or **Not installed or not provided (n)**. Select a grouped section to open its explanation, which lists the refused reads and their DSM APIs and names the signed-in account. **Could not verify** sections stay in the list.

Most administration data is administrator-only in DSM: resource usage, storage, shared folders, network, users and groups, packages, services, security, UPS, power schedule and system logs. The Container Manager, Virtual Machine Manager, Hyper Backup and Active Backup for Business packages are administrator-only too. DSM 7.2 delegated administration can let another account view some of this data, which is why each read is checked instead of inferring access from the account's role. For a standard or delegated account, the session panel notes that administrator-only data is hidden.

Restricted reads are not requested when a section opens, on **Refresh** or by the 30-second refresh; their tables show the notice instead. If DSM refuses a read (code 105) before the check has classified it, the table shows the notice rather than an error, and that section is rechecked once automatically. **Recheck access** on a notice rechecks its section, and **Recheck section access** under the sidebar rechecks every section. Data a recheck finds readable loads straight away. DSM may apply privilege or group changes only at the next sign-in, so if data stays restricted after you change DSM, reconnect.

Actions that need an administrator are disabled, with the tooltip **Requires a DSM administrator account**, only when every read in their section requires an administrator. With partial or delegated access they stay available, and DSM still checks each action when it runs.

DSM code 120 means DSM didn't accept a request's parameters. It is not a permission denial: the access check shows **Could not verify**, and a table load that gets 120 appears under **Some data could not be refreshed** without a restriction, so **Refresh** tries it again. The NAS may expect a different request on its DSM version; update the desktop app, and copy the diagnostics if it persists.

Firewall rules are read for each network adapter DSM lists, up to 32 adapters. SMART details for a disk are not requested while the Disks read needs more access. If DSM doesn't recognize the SMART method (code 103), the app asks once more with DSM's health-information method.

The legacy commands `syn_connect`, `syn_disconnect`, `syn_is_connected`, `syn_check_session` and `syn_get_config` are compatibility plumbing, not an alternate login path for saved sessions. Legacy `syn_list_files`, `syn_list_file_shared_folders`, `syn_search_files`, `syn_upload_file`, `syn_download_file`, `syn_create_folder`, `syn_delete_files`, `syn_rename_file` and `syn_create_share_link` are replaced in this interface by the receipt-bound File Station family. `syn_get_camera_snapshot` is replaced by the bounded typed snapshot command. Their presence does not authorize bypassing a saved session's ownership, route or certificate checks.

This interface does not add unsupported ACL editing, VM restore, backup restore, remote mounts, archive extraction, arbitrary scripts or package upload. Browser-only DSM authentication must use the actual DSM origin in a normal browser; a localhost-proxied website may not support origin-bound security keys. Its cookies remain separate from this API login.
