# Device SSL/TLS compatibility

The private intercepting proxy supports these device-facing profiles:

| Saved `browserSession.upstreamTlsProfile` | Protocols | Engine |
| --- | --- | --- |
| `modern` (default) | TLS 1.2 and 1.3 | Rustls |
| `tls12` | TLS 1.2 only | Rustls |
| `tls13` | TLS 1.3 only | Rustls |
| `tls11` | TLS 1.1 only | Legacy helper |
| `tls10` | TLS 1.0 only | Legacy helper |
| `ssl3` | SSLv3 only | Legacy helper |
| `ssl2` | SSLv2 only | Legacy helper |
| `legacy` | SSLv3 through TLS 1.2 | Legacy helper |

Choose **Device SSL/TLS compatibility** in the connection editor's browser
session options. The sparse connection override inherits the app's
`webBrowser.upstreamTlsProfile`; the default is `modern`. For example:

```json
{"browserSession":{"version":1,"tlsInterception":"auto","upstreamTlsProfile":"ssl2"}}
```

A non-default profile requires active backend TLS interception. An attempt
fails if interception is disabled or unavailable; it never delegates the
legacy handshake to Chromium. SSLv2 must be selected explicitly and is never
included in automatic legacy negotiation. The selected policy applies to
all admitted upstream authorities in that connection attempt, including
secondary resources and redirects. It grants no additional destinations.

The browser-facing connection continues to use modern TLS. The helper has
no socket or DNS code in its entry point: its bounded binary pipe protocol
exchanges encrypted records with the existing `RouteDialer` stream. It
receives an SNI name but no destination port, route, proxy credentials, or
request before certificate admission. Process separation is not an OS
sandbox, and obsolete device-facing encryption remains vulnerable.

The proxy retains certificate structural checks, OS validation/revocation,
HSTS enforcement and Trust Center admission before sending HTTP bytes. This
setting does not override revoked certificates or invalid signatures.
The separate **Allow weak device certificates** option
(`browserSession.allowWeakCertificates`, default false) permits small RSA
keys and obsolete certificate signatures. Trust Center admission still
applies. Modern Rustls profiles may lack the required cryptography; select
an explicit legacy profile for those devices. Persistent Trust
Center admission permits the normal per-connection cache, subject to the
site's HTTP cache policy; allow-once admissions never persist responses.
Legacy upstreams use HTTP/1.1.

## Build and packaging

```sh
npm run native:legacy-tls:build -- --test-fixture
npm run native:legacy-tls:test
```

Requires Node, Perl, GNU make, a C compiler, and tar. On Windows the script
uses MSYS2 MinGW64 when installed at `C:/msys64`; otherwise set `CC`, `MAKE`,
and `PERL` and put the tools on PATH. `LEGACY_OPENSSL_TARGET` selects an
OpenSSL Configure target; `LEGACY_TLS_JOBS` controls compilation parallelism.
Run separately for each target architecture. Windows ARM cross-builds need
an appropriate compiler and explicit Configure target; they are not implied
by an x64 build. Linux/macOS targets require native validation on those hosts.

The script downloads OpenSSL 1.0.2u, verifies its pinned SHA-256 from the
[OpenSSL release announcement](https://mta.openssl.org/pipermail/openssl-users/2019-December/011675.html),
and statically links it into `native/legacy-tls/bundle/sorng-legacy-tls`
(`.exe` on Windows). This obsolete library is isolated from the main app's
Rustls backend. The bundle also includes the OpenSSL license and a receipt
with platform, architecture, source hash and helper hash.

The production Tauri build hook builds the helper before packaging, and the
resource mapping installs the bundle under `legacy-tls/`. Custom build hooks
that bypass `beforeBuildCommand` must stage it explicitly. An empty source
checkout does not contain a prebuilt helper. A missing helper is reported as `tls-legacy-unavailable`;
there is no network download or direct-network fallback at runtime.
For development, `SORNG_LEGACY_TLS_HELPER` can select an absolute helper path.
Packaged sessions resolve their helper from the native resource directory.

The optional test server is built only with `--test-fixture`. Native helper
tests perform real SSLv2, SSLv3, TLS 1.0, TLS 1.1 and legacy negotiation,
bidirectional data transfers and a version mismatch. The ignored Rust
integration test `real_legacy_profiles_obey_route_and_certificate_admission`
additionally needs `SORNG_LEGACY_TLS_HELPER` and `SORNG_LEGACY_TLS_FIXTURE`
pointing at the built executables. Test certificates are generated by the
Node tests under the ignored build directory.

## Failure reporting

The synthetic error page and `X-Sorng-Error-Code` distinguish version,
cipher, signature-algorithm, key-exchange and ALPN incompatibilities;
malformed handshake data; decryption failures; peer alerts; resets; early
EOF; handshake deadlines; and helper availability/protocol failures.

The peer's generic `handshake_failure` alert is reported as alert 40, with
its ambiguity explained. It is not asserted to be a cipher or certificate
failure. Other alerts retain their numeric value. Unclassified legacy
engine failures retain their numeric OpenSSL error code. Reports never
render arbitrary native error text, hostnames, URLs, credentials or paths.
