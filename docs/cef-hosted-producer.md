# Hosted CEF producer prerequisites

The engineering workflow has four explicit modes. Its existing default, **build**, still requires reviewed input locks, dedicated runners and the protected default-branch publisher. **discover** gathers observations on six fixed standard public runners. **provision** prepares reviewed prerequisites and uploads unreviewed post-install inventories. **hosted-build** replays that prerequisite preparation, verifies reviewed image/toolchain pins and builds real engine bundles on fixed public runners. Hosted modes never publish automatically.

Run discovery with `mode=discover`, `publish=false`, and the existing required `reviewed_inputs`/`target` inputs (they are not consumed by discovery). Leave `discovery_cleanup_linux=false` initially. Discovery can run on a reviewed branch because it has no write permission or protected-environment secrets.

Each `cef-hosted-discovery-<target>` artifact contains actual image identity, OS/CPU/RAM/disk observations, Python/compiler/Xcode/SDK paths and versions, real file sizes and SHA-256 hashes, and explicit blockers. `toolchain-candidate.json` is **UNREVIEWED**. A successful observation job is not evidence that Chromium compiled, that a toolchain is complete, or that a target passed native acceptance. Missing tools remain blockers, with no version downgrade.

The reviewed Chromium source requires Visual Studio 2026 and the Windows SDK 10.0.28000 line. The fixed x64 discovery label therefore explicitly selects `windows-2025-vs2026`; the ARM label is `windows-11-arm`. Actual observations must still verify required files. If installation is necessary, first review an exact signed Microsoft installer and its hash. Discovery never downloads or runs that installer.

## Explicit prerequisite provisioning

After reviewing the committed commands, dispatch `mode=provision`, `publish=false`. Linux x64 needs the explicitly reviewed `discovery_cleanup_linux=true` option to recover enough disk space. Provisioning can run from a reviewed branch and has a 30-minute job budget. It is refused outside an explicit public GitHub-hosted workflow dispatch; it cannot install on a local or self-hosted machine.

Windows downloads only the exact Microsoft SDK28000.2270 installer pinned in `native/cef-hosted-recipe.json`, verifies its byte hash, Valid Authenticode signature, exact Microsoft signer and product version, then executes fixed quiet/no-restart/no-CEIP DesktopCPPx64/DesktopCPParm64/WindowsDesktopDebuggers features. Any nonzero exit, including a reboot request, stops the preparation. No automatic reboot or Visual Studio installation is attempted.

Linux verifies the exact Chromium-commit `install-build-deps.py` hash and invokes its fixed no-prompt/no-syms/no-ChromeOS-fonts/no-ARM-cross/no-backwards-compatible options. The upstream script updates apt metadata, installs dependencies and configures build locales on this expendable runner. It runs with no GitHub or Actions tokens in the child environment. Resolved package versions and before/after native tool inventories are retained for separate review. These are actual observations, not a hermetic toolchain claim.

macOS provisioning only observes its existing tools; it downloads or installs no Xcode. The small ARM runner is reserved for eventual native acceptance rather than a claimed cold Chromium build. Windows tools are probed using a fixed installed PowerShell whose actual PE architecture matches the host, with a bounded 90-second native startup. A failed probe records only fixed stage/timeout/exit metadata and leaves tool availability unknown.

## Reviewed hosted builds

`mode=hosted-build` allows an explicitly dispatched reviewed branch in this public repository, without protected-environment secrets or write permissions. This allows real bundles and acceptance checks before the final default-branch release merge. The dedicated build and protected publisher remain default-branch-only. Hosted builds require real reviewed source-lock inputs: Version2 runner maps add an exact fixed runner, ImageOS/ImageVersion, build OS/architecture and native acceptance runner to the existing pinned map. The full map bytes remain pinned by the toolchain lock. A changed image, unreviewed map, different architecture or excessive parallelism fails before source acquisition. Native tools are rehashed after prerequisite preparation; missing pins are never generated by a build.

Hosted parallelism is capped at two sync workers and four build workers, with the reviewed worker count no greater than the actual CPU count. Less than100GiB free space or8GiB RAM stops the build. One shared monotonic300-minute engine budget spans source sync/build/package stages; it is not reset for every command. On expiry the producer attempts to stop only its exact spawned process tree/group and records the cleanup outcome and failure logs. The350-minute job bound leaves time for prerequisite replay and diagnostic upload. Existing source acquisition, patch checks, archive inventory/extraction roundtrip and target binary architecture/export validation still run.

The single allowed cross-build is `aarch64-apple-darwin` on the fixed Intel Mac runner, with an image-bound x64 tool inventory and target_cpu=arm64 GN pin. Actual framework/sandbox Mach-O architecture is checked; host architecture never stands in for target architecture. Its declared native acceptance runner is the ARM `macos-15` runner. The existing acceptance copier is Windowsx64-only: native acceptance adapters for the other targets remain a separate required gate, and hosted bundles remain `nativeAcceptance: not-tested`/`productionReady: false` until that real work completes. Consequently hosted mode cannot enter the protected publisher.

Only the fixed reviewed runner-map filename is staged at the tools volume root before its hash is verified again alongside the native tool inventory. A different existing file is never overwritten. No arbitrary installed tool path is written. The default dedicated runner map schema/behavior remains unchanged.

On Linux only, an explicit cleanup dispatch can remove the four fixed expendable SDK directories listed in `native/cef-hosted-recipe.json`. The helper requires a public GitHub-hosted Linux runner, exact canonical non-symlink roots, and no overlap with checkout or runner workspaces. It records before/after free space and each removed root. There is no arbitrary cleanup path input. Do not enable cleanup until its concrete list has been reviewed for that image.

## Next build phase

1. Review the six actual observation artifacts and resolve every prerequisite blocker. Pin the actual runner map, Python/native tools and GN bytes in source-lock inputs; do not promote discovery output automatically. Changed hosted images must fail existing hash verification until reviewed again.
2. Use the reviewed hosted build contract with its350-minute work budget and retained diagnostics. Estimate cold source sync/build feasibility from real milestones and stop with evidence rather than claim an unfinished engine is usable.
3. The macOS ARM64 target may use upstream-supported Intel-to-ARM64 compilation only after an explicit same-OS cross-build contract, target GN pin and actual Mach-O architecture verification. It still needs a separate native ARM64 acceptance job. This discovery phase deliberately rejects architecture mismatches.
4. Reuse only immutable, verified finished bundles or explicitly source-lock/toolchain/image/GN-keyed checkpoints with bounded storage and revalidation. Do not assume a large Chromium tree fits a standard repository cache or that an incomplete object tree proves acceptance.
5. Require all six verified bundles **and** all six native acceptance receipts before publishing the set and reviewing consumer catalog hashes. The user's chosen release policy is to wait for all six, not publish a Windows-only release.

The existing accepted local Windows ACK package may be repackaged into a new immutable publication bundle, but it does not stand in for the other five targets or a hosted runner receipt. No current runtime selection or user process is changed by discovery.
