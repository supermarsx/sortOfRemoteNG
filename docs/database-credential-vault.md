# Database credential vault

Open **Database Credential Vault** from the toolbar's Management group, or use **Settings → Security → Database credential vault → Manage database credentials** to open the same dedicated tab. Repeated activation focuses the existing vault for that database in the main window. Vault tabs cannot detach or move between windows: private drafts are never transferred. Detached Settings directs you to the main-window toolbar. **Settings → Layout** controls the toolbar shortcut; hiding it does not disable the vault. Each database owns an independent vault. Open and unlock that database first; the native desktop app verifies either managed database protection or effective app-wide encryption covering connection data with authenticated on-disk protection proof. An unlocked app-wide key alone is not enough. App-wide encryption does not create a shared global vault: credentials remain database-owned, with no plaintext or other-database fallback and no automatic migration from connection-local credentials, the rotation tracker, or integration credential stores.

Create an entry with a name and one or more credential types: username, password, domain, private key, key passphrase, or TOTP authenticators. Secret fields start masked; reveal a private key to edit its multiline contents. TOTP entries contain an existing Base32 seed and its digits, period and algorithm—not a current one-use code. This editor does not enroll an authenticator or submit codes.

## Credentials already saved in connections

The inventory defaults to **All sources**: reusable vault entries plus one virtual row for each saved connection containing credential fields or references. **Source** filters to **Reusable vault** or **Connections**. Search matches connection names, protocols, fixed credential-type labels and storage-source labels—not usernames, passwords, URIs, file paths, reference IDs or arbitrary header names. Counts distinguish reusable records from connections; a connection with several credential fields is still one row, not several copied credentials. The table shows 25 rows per page.

Choose **Edit in connection** to open the authoritative connection editor. Native protected-storage verification runs again before opening it, and the current connection is looked up in the same owning database. Connection edits and deletions refresh the inventory; locks and database-owner changes remove access. There is no automatic migration, duplicate secret store, new clipboard action or inventory export. **Export archive** still exports only deliberately selected reusable vault credentials and their supported linked connections. It does not include connection-local secrets merely because an inventory row is visible.

**Connection-local**, **Database vault link** and **External reference** describe storage, not proof that a credential works. Local login values retained beside a vault link do not become a fallback. Integration OS-vault records, PowerShell store references and client-key files are indicated without opening those stores or reading those files; edit their configuration through the connection editor and the owning integration/store controls. Unrelated global rotation entries, saved shared route/VPN stores, session-only integration secrets, remote browser cookies and hardware-authenticator private keys are not database-owned credentials and are not enumerated. Recycled connections remain in the Recycle Bin until restored.

### Saved-field coverage

The projection follows concrete connection schemas; it never recursively searches arbitrary object values for secrets. Developer regression fixtures cover these families:

| Family                 | Presence detected, values never listed                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account authentication | Username/domain, password (including explicitly blank password with an account), RustDesk password, private key/key path and passphrase                                                                             |
| MFA and recovery       | Legacy TOTP seed, named TOTP seeds/backup codes, security answers and recovery contact/seed fields                                                                                                                  |
| Websites               | Basic authentication, custom header values, proxy query parameters and literal automation form fields                                                                                                               |
| Databases and clouds   | MongoDB connection URI; current cloud token/JSON password storage; legacy cloud API keys, access tokens, client secrets, service-account keys and OVH secrets                                                       |
| RDP                    | Separate gateway account/password/access token; routing cookie/token                                                                                                                                                |
| Inline network routes  | Legacy proxy authentication/key/tunnel headers; chain proxy passwords, SSH key/password/passphrase and ProxyCommand credentials; VPN private/pre-shared keys, mesh authentication keys and tunnel tokens            |
| SSH overrides          | ProxyCommand authentication and mixed SSH/proxy-hop passwords, key references/passphrases, authenticators and keyboard-interactive answers                                                                          |
| External references    | PostgreSQL/MySQL/Mongo client-key files; PowerShell credential/key/client-certificate/proxy references; integration persisted `credentialRefId` / named `credentialRefIds`; same-database reusable vault references |

FTP, VNC, SPICE, X2Go, NX, ARD and other protocols using the generic connection account/password/key fields are included independently of reusable-vault runtime support. SPICE's potentially credential-bearing proxy URI is indicated without displaying it. Merely selecting an authentication method or a server CA certificate does not imply saved credentials. Unknown plugin fields, scripts, environment variables and arbitrary JSON blobs are not inspected or interpreted.

Focused checks: `node node_modules/vitest/vitest.mjs run tests/security/connectionCredentialInventory.test.ts tests/security/ConnectionCredentialInventory.test.tsx tests/security/DatabaseCredentialVault.test.tsx tests/connection/DatabaseCredentialVaultPersistence.test.tsx --maxWorkers=2`. The Provider fixtures exercise managed and native-proven global protection, actual connection updates without vault creation, and pending-editor revocation. These are local synthetic tests, not logins against real services.

Social sign-in and passkey entries are **metadata only**, explicitly marked `portable: false`. Their descriptive metadata can travel inside an encrypted vault archive, but OAuth sessions, browser cookies and authenticator private keys cannot. They describe a provider and starting website HTTPS origin or relying-party domain. Sign-in still requires the original website/browser and provider or authenticator.

In a connection's **General → Credential source**, choose Connection-local or Database vault and select a same-database entry by name. The picker loads only names and available credential types. It saves a reference, not a secret copy. Existing local fields are preserved but ignored while the vault reference is selected. Runtime support is adapter-specific: an unsupported or missing reference must fail closed rather than use local credentials. Adding a reference does not imply every protocol supports every credential combination.

Editing explicitly loads that entry's facets into the private draft. Changes save atomically against the reviewed database revision; a conflict, failed save, lock or owner change does not publish an optimistic replacement. Preserve the draft and reload/review before retrying a failed save. Closing the editor asks before discarding changes; locking or changing the database immediately removes the private editor. Deleting a vault entry does not revoke it at the remote service and can leave connections requiring a replacement.

Vault payloads remain separate from connection and session state. Runtime adapters and portable export/import are separate integration boundaries; this manager does not promise portable social sessions, passkeys, or support in every export format.

## Connection runtime support

**Hardware Keys** is a separate toolbar tool for the existing YubiKey manager. Settings → Security → Manage YubiKeys opens the same tab; its Layout visibility flag is independent of the vault shortcut. It requires the full native desktop build and ykman, not an unlocked database. Opening either tool does not unlock storage, approve a website or enroll a hardware key. Vault tabs have no duplicate Close button: the normal tab close asks before discarding a private draft and waits for in-flight vault operations. Manual database switching or closing also requires pending vault work to be saved or discarded; locks and owner revocation still remove inaccessible private content.

The connection-session adapters support **SSH password/key/TOTP**, **RDP username/password with optional domain**, **HTTP(S) Basic, Digest or reviewed website form profiles**, and **Synology NAS API / File Station**. Each attempt verifies the saved target/reference and owning protected database, then resolves only the required facets. No resolved secrets are saved on a connection, session, or the global runtime-connection registry. Failed or missing references stop before connection automation; they never use preserved local login values. Reconnect and reattachment repeat the access checks. FTP, VNC and other unlisted protocols are not covered.

SSH password mode requires a nonempty password. Key mode uses private-key text in memory, with an optional key passphrase and account password for servers requiring both key and password. It does not create a temporary private-key file. RDP preserves an explicitly present empty password and does not substitute a connection-local domain when the vault has none. Website manual navigation does not automatically disclose login credentials. Website TLS/trust and same-origin boundaries remain unchanged. Connection-local custom headers/cookies and literal form automation fields cannot be combined with vault website login. Cross-origin redirect forwarding does not carry vault credentials or references.

For automatic server challenges, explicitly select **Vault authenticator for login challenges**; no first authenticator is chosen implicitly. SSH and Synology use the selected authenticator only for supported code challenges. Synology generates once after OTP-required, never automatically retries an invalid code, and retains manual verification. HTTP automatic MFA additionally requires saved consent for a reviewed profile challenge and exact HTTPS origin. Unsupported forms, push approval and enrollment stay interactive. SSH, RDP and HTTP sessions also provide a manual **Vault authenticator codes** panel: generate and copy explicitly, with no automatic paste or submission. Local authenticators are ignored when vault credentials are selected.

The HTTPS website **Vault social and passkey sign-in** control explicitly opens a matching binding at the original website in the external browser. Exact social-origin and passkey relying-party/public-suffix checks apply; the browser and authenticator perform the actual ceremony. This does not transfer cookies into the embedded tab or claim successful login. It cannot clone a hardware authenticator.

Referenced SSH jump/bastion hops currently require connection-local credentials; a vault-backed or invalid hop reference is rejected before any local or inline fallback. Auxiliary bulk, tunnel and diagnostic workflows are separate adapters, not covered by the session-adapter support claim. An isolated loopback OpenSSH container verified in-memory encrypted key use and key-plus-password authentication; RDP, website, Synology and authenticator behavior have fixture coverage, not live deployment acceptance. See the [login steps and acceptance matrix](credential-vault-portability.md#acceptance-matrix) for exact evidence and limits.

## Moving connections between databases

Use **Export archive** in the database vault to select credentials and optional linked connections, then **Import archive** in the destination vault. The password-protected `.sorngvault` archive is authenticated ciphertext, not JSON containing exposed secrets. Review the decrypted names and counts before import. Credentials and connections append in one protected atomic save with fresh credential, connection and authenticator IDs; references are remapped together and existing records are not overwritten.

Ordinary selected-connection imports, exports and clones cannot safely carry bare database-vault references. They refuse that operation even if the destination has a matching ID, and direct you to the encrypted archive instead. Ignored local credentials are never substituted. A generic JSON import declaring a vault, or an encrypted archive opened through the wrong importer, is rejected rather than silently dropping records.

The archive is a credential bundle, not a whole-app backup. Linked connections must reference included credentials; unsupported saved-route and script/macro-library dependencies are rejected. Connections import at the database root, with no source folder hierarchy. Custom icon keys survive but separate icon assets do not travel. Automatic login/MFA/automation and redirect grants require fresh local review; certificate and host-key checks start fresh. Social/passkey metadata does not transfer active sessions or private authenticator keys. See [encrypted vault archives](credential-vault-portability.md) for limits, protection, password requirements and the full import/export workflow.

The separate [Documents feature](database-documents.md) also accepts unlocked managed protection or native-verified global Connections encryption of the owning file, including an unlocked OS-vaulted global key. Merely enabling a preference or unlocking a key does not protect a plaintext file. Vault archives do not include documents or attachments.
